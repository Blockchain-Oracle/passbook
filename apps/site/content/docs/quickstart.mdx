---
title: Quickstart
description: From opening the page to a protected, registered account with shielded value.
---

There is no email login or extension to install. There is still a setup flow, because key
protection, recovery and registration are decisions a money account must not hide.

<Steps>

<Step>

### Create the browser account

Press **Create an account**, learn the two-balance model, choose an optional label and decide
whether to claim that label publicly. On the protection screen, choose a password, passkey, both,
or neither, then generate the key.

Passkey setup uses two approvals and another-device recovery has explicit compatibility and sync
conditions. Read the [Passkey architecture](/docs/how-it-works/passkeys) before treating it as a
backup.

<Callout type="warn">
A password or passkey seals the account record in an encrypted vault. Choosing neither stores the
key in browser storage in plaintext, readable by scripts on the origin and by someone holding the
unlocked device.
</Callout>

</Step>

<Step>

### Save the Recovery File and Code

Issue the file, write the code somewhere else, type it back and download the verified file. The
registered key cannot be replaced, so recovery is completed before the first on-chain write.

</Step>

<Step>

### Deploy the account, then register

An account contract has to exist on-chain before it can sign anything, so the app deploys it. Then
it **registers** with the pool.

Registration is the step to read twice. It publishes an encrypted copy of your viewing private key
on-chain, readable by anyone, decryptable by the auditor. It cannot be rotated and cannot be opted
out of. [The auditor](/docs/privacy/the-auditor) explains exactly what that means.

The app attempts its current faucet and sponsorship offer. Those are live services with budgets,
so the setup screen also provides the public address to fund with STRK when either is unavailable.
There is a [recorded sponsored registration on mainnet](/docs/evidence).

</Step>

<Step>

### Shield public value

You send tokens into the pool from a public address. **This step is public**: an observer sees your
address and the amount. That is not a limitation of strk20.run, it is what a deposit is.

Deposits are also screened by a third-party provider the pool operator chose. A refusal is silent —
if a deposit does not arrive, it will look like our bug.

</Step>

<Step>

### Send or use another surface

Inside the pool your value is a set of shielded notes. From here the surfaces do what they say:
sends are private to everyone except your recipient; Mail attaches a sealed memo to one of those
sends; Earn, swaps and bridges use
[the invoke sandwich](/docs/how-it-works/invoke-sandwich) so value never lands on a public address
of yours in between.

Chat is the separate gas-free lane. Its messages use the relay rather than the chain, and its local
history does not recover from the account key. [Compare Chat and Mail](/docs/how-it-works/chat)
before choosing between them.

Amounts on any leg that touches an open note remain public. **What is hidden is who.**

</Step>

</Steps>
