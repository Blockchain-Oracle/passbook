## 1. Product

One app: **hold, send, swap, bridge, message, bet and launch tokens privately** on Starknet's STRK20
privacy pool. The shape is Uniswap's — many primitives that feel like one product. The register is a
precision instrument, not a marketing site.

**The positioning, which drives real design decisions:** every competitor claims privacy and hopes
nobody checks. This product **shows the user their true anonymity set at the moment of decision**.
Verified: no shipped privacy product does this — Railgun, Privacy Pools and Railway were all checked.

### 1.1 Surfaces

| Surface | Build | RFP |
|---|---|---|
| **Wallet** | Register viewing key on first use · publish a receive address · run discovery · send as Withdraw/CreateEncNote. **No new contracts.** The substrate, not a tab | Idea 10 |
| **Chat** | Pool-rooted ECDH (**free** — both public keys are already on-chain) · off-chain encrypted transport · chain used for room-open, seal, and money-with-message | Idea 01 |
| **Swap** | `ValueRouter.SWAP` — approve venue, execute, measure output by balance delta, return the deposit. **Venue pinned at deployment.** AVNU routing API for multi-hop | IDEAS.md IDEA-01 |
| **Bridge** | `ValueRouter.BRIDGE_FORWARD` — **outbound only** via CCTP v2. Circle's Forwarding Service pays destination gas | Idea 22 |
| **Markets** | FPMM binary UP/DOWN, Pragma-resolved, 3-strike ladder | Idea 07 |
| **Launch** | Epoch-clearing auction, six public denominations, Ekubo graduation with router-owned LP | Ideas 04 + 17 |

**Out of scope:** yield, savings, the card, the AI-agent framing (D8); inbound bridge (D24, stretch);
confidential voting (D26, stretch); the eight RFPs built on the non-existent "Enclave".

## 2. Identity

### 2.1 The model

```
PrivateIdentity {
  key      locally-generated Stark keypair, in-browser
  backup   Recovery Code (generated, never seen by us) + encrypted Recovery File
  viewing  registered on-chain — this IS the STRK20 identity
}
```

**Never derived from a wallet signature.** The registered key is WriteOnce-immutable with no rotation
path; 46 of 51 measured registrants are Ready smart accounts across **two class versions**, proving
upgrades happen in the wild and would permanently orphan a signature-derived key. A passkey may *wrap*
the key for device lock; it must never *derive* it.

**UI vocabulary:** "Account Key" everywhere. "Viewing key" appears only inside technical disclosure.
A fixed definition travels with every rendering: *"Reads your notes. Signs your spends. There is no
read-only version."*

### 2.2 State machine

```
AccessPattern      = Native | Injected
SigningCapability  = None | Interactive | Immediate
RegistrationState  = Unregistered | Registering | Registered | ForeignKey
```

`ForeignKey` guards the collision case: if `get_public_key(addr)` is already non-zero from another
STRK20 app, registration **can never succeed** and discovery silently returns nothing. The free
pre-flight read runs before every create and restore. **If the RPC is down, block — never proceed on
an unknown.**

Every feature asks the store one question: *"give me the active account and whether it can sign."*
No feature knows which wallet answered.

### 2.3 Ready wallet

A **funding rail, never an identity.** It appears only in shield and cash-out flows. The UI shows
exactly one address: the private receive address.

### 2.4 The bootstrap deadlock — and the fix

Verified on mainnet: `open_channel` asserts `RECIPIENT_NOT_REGISTERED` (cannot pay an unregistered
address) · the paymaster fee is withdrawn from the user's **shielded** balance (which a new account
lacks) · `collect_fee` pulls from whoever submits. **A fresh account cannot bootstrap itself.**

**Fix:** our relayer sponsors the first registration. Registration is a zero-deposit `SetViewingKey`,
which sets no screening subject, so a sponsored registration should be AML-immune — **verified for the
invoke path, LIKELY only for the registration phase. One sponsored registration must be banked on
mainnet in week one before the invite flow ships.**

## 3. Submission — our own relayer

~150 lines of TypeScript plus one funded hot account, implementing the sponsor's injectable `Paymaster`
interface. `buildTransaction` returns a withdraw to our relayer address; `executeTransaction` posts to
our server, which submits.

Legal because `apply_actions` has **zero caller access control** and `collect_fee` pulls from
`get_caller_address()`. On-spec because Idea 03 states the sponsor's own position that *"paymaster
submits, no address link"* is **the** mechanism for sender anonymity.

Solves four problems: the bootstrap deadlock · sender anonymity · keeping any third-party credential
out of the public bundle (AVNU's key is read from `VITE_AVNU_API_KEY`, which Vite **inlines into
browser JavaScript**) · rate limits during judging.

### 3.1 What the UI is allowed to promise, and when

Every Starknet transaction **publicly shows which account submitted it and paid the fee.** That is not
hideable. So the only question is *whose* address appears there.

- **Self-submitted:** the public record shows *the user's own address sent a transaction to the privacy
  pool at 14:32.* Their note contents stay hidden, but the fact that **they** used the pool does not.
- **Relayer-submitted:** the public record shows **our relayer's** address. The user's address appears
  nowhere. This is the entire reason the relayer exists.

**Therefore the confident sentence ships only after the relayer is proven working on mainnet.** Writing
*"your address never appears"* into the UI before that would tell every user something false — and a
judge disproves it in one call by opening a transaction and reading the sender field. That is an
overclaim on the criterion worth 30%.

**Ship this sentence first — it is accurate in both cases and never has to be walked back:**

> *"The pool sees your transaction, not your notes. Your wallet address is the visible submitter of
> this transaction; the link between your address and the specific note being spent stays hidden."*

Upgrade the copy only once the relayer demonstrably works. **Rule: never promise a privacy property in
the interface before the mechanism that delivers it is proven.**

**Degraded mode:** if the relayer is down, offer self-submit with the honest tradeoff shown — the
user's address becomes visible, and they must hold STRK **and** a standing ≥6 STRK approval to the pool.

## 3.2 Networks — config, not environment variables

**Selection is a build-time constant.** One line names the active network. Production builds are always
mainnet; there is **no runtime network switch in the shipped app.** The elimination gate depends on a
judge seeing real mainnet state, and there is no upside to letting that be switchable in production.

**Network parameters are a typed constant, not environment variables.** They are facts about a network,
not deployment secrets — they belong in version control where they can be reviewed and diffed. Adding
a network means adding a key, not hunting for `process.env` calls.

```ts
export const NETWORKS = {
  mainnet: { chainId, pool, rpc, prover, discovery, explorer },
  sepolia: { … },
} as const

export type NetworkName = keyof typeof NETWORKS
export const ACTIVE_NETWORK: NetworkName = 'mainnet'   // the one line that changes
export const NET = NETWORKS[ACTIVE_NETWORK]
```

**Environment variables are reserved for secrets only** — the deployer key and the relayer key. Nothing
else.

### 3.2.1 What is verified about Sepolia (21 Aug 2026)

**Conclusion, from source: there is no publicly-addressable STRK20 pool on Sepolia to point at.**

| Component | Status |
|---|---|
| Prover `transaction-prover.alpha-sepolia.sw-dev.io` | ✅ **Live.** POST → `200`, same as mainnet |
| A shared Sepolia pool we can use | ❌ **Does not exist as a published address** |
| Pool address / class hash anywhere in the SDK | ❌ **The entire `sdk/` + `client/` source contains exactly ONE long hex constant** — the STRK fee token `0x04718f5a…c938d`, which is identical on every network. `poolAddress` and `poolClassHash` are **runtime parameters** (`requireEnv("VITE_POOL_ADDRESS")`), never constants |
| The sponsor's demo | Ships **`demo/src/hooks/useDeployPool.ts`** — you deploy your own pool |
| Discovery service | ❌ `404` — the mainnet host answers; this one does not |
| The sponsor's own dev setup | ⚠️ **Not public Sepolia** — chain ID decodes to `SN_INTEGRATION_SEPOLIA`, with localhost RPC/prover/indexer; they deploy their own pool via `e2e/scripts/` |

The SDK changelog's *"pinned class hashes of the deployed pre-screening pools on SN_MAIN and
SN_SEPOLIA"* describes behaviour where **the application supplies those hashes**, not constants a
consumer can read. **Asking the sponsor for "the Sepolia pool address" would not produce a useful
answer — there is no shared testnet pool to hand out.**

**Consequence — the recommendation inverts.** We *could* deploy our own Sepolia pool with the sponsor's
`e2e/scripts/`, but we would then be testing against **our** pool rather than the one being scored.
**`compile_actions` validates against the actual deployed mainnet contract, for free** — strictly
better for every question that matters, with no drift risk and no setup day.

**So: keep the network config layer** (cheap, correct, and `sepolia` can be filled the moment a shared
pool exists) **but do not stand one up.** Testing leans on `snforge` + `compile_actions`, and real
transactions cost ~$0.25 each on the network that counts.

### 3.2.2 The four testing layers

| Layer | Cost | Answers |
|---|---:|---|
| `snforge` | free | Does the Cairo do the right thing? **Most testing lives here** |
| **`compile_actions` on mainnet** | **free** | Would the *real deployed pool* accept this action list? A public view running the real client compiler — verified to compile 100 notes + 1 invoke, with negative controls |
| Sepolia | free | Full prove → submit → settle round-trip, once the address is known |
| Mainnet | ~$0.25/tx | The real thing, and the only thing that scores |

`compile_actions` is strictly better than Sepolia for action-list validity, because it validates against
the **actual contract being scored** rather than a different deployment that may have drifted.

### 3.2.3 The guard that must exist

Rival `veyl` has **Sepolia addresses in a mainnet array** in its `strk20.json` and **scores zero.**
A build-time check must refuse to write any non-mainnet address into `strk20.json`, and must fail the
build if `ACTIVE_NETWORK !== 'mainnet'` when producing a production bundle. Same shape as the claims
lint: make the mistake mechanically impossible rather than something to remember.

**⚠️ Oracle asymmetry, in the dangerous direction.** Chainlink on Starknet is **Sepolia-only**. Anything
oracle-touching must therefore be validated against **mainnet reads even during development** — building
markets on a feed that works on testnet and does not exist on mainnet is precisely the
"discovers-the-dependency-in-week-two" failure, self-inflicted.

## 4. Contracts

Four separate contracts. A six-mode monolith buys **zero** atomicity (the pool permits one invoke-phase
action per transaction either way) while costing **unlinkability** (`identity_key` is scoped per
`contract_address`, so one contract = one stable pseudonym across every merged mode) and **blast
radius** (a stateful multi-mode contract holding value is drainable by an anonymous caller).

| Contract | Cairo | State | Caller guard |
|---|---:|---|---|
| `MessageBook` | ~170 | append-only ciphertext by tag | permissionless OK |
| `ValueRouter` | ~330–400 | **none** | — (stateless) |
| `PredictionMarket` | ~700–1,000 | per-identity balances | **`assert(caller == pool)`** |
| `LaunchRouter` | ~380–620 | per-identity allocations | **`assert(caller == pool)`** |

**Unify only where two effects must land in one invoke** — exactly two cases exist:
`TRANSFER_WITH_MEMO` (Idea 01's payment memo, which separate helpers provably cannot do) and
`BRIDGE_FORWARD` (verified: swap → public payout **is** one transaction).

### 4.1 Security rules — non-negotiable

- **Stateless helpers:** no storage, no balance, **never leave a standing allowance**, assert own
  end-of-call balance is zero. Never accept a caller-supplied arbitrary `Span<Call>` — pin the venue at
  deployment.
- **Stateful helpers:** `assert(get_caller_address() == pool)` the moment per-user state exists.

### 4.2 Protocol constraints every contract must respect

- **One invoke-phase action per transaction**, in the fixed 7-phase order. But **N×UseNote,
  N×CreateOpenNote and M×Withdraw are all legal in one transaction** (D28), and **one invoke may credit
  N notes** — verified by compiling 100 notes + 1 invoke through the free `compile_actions` view.
- **Every invoke-bearing transaction must also carry a WriteOnce action** — a 1-wei note or an
  `OpenSubchannel`. An invoke-only transaction is illegal.
- **Channels open in strict sequential index order** (`INDEX_NOT_SEQUENTIAL`). Parallelism is a revert,
  not an optimisation. Any fan-out feature needs a per-sender monotonic index.
- **Deposits returned must exactly equal notes created**; **zero-amount deposits revert**; return a
  **bare `Span<OpenNoteDeposit>`** — the HEAD tuple signature reverts on the deployed class.
- Pin to the deployed class tag `CONTRACT_V2_DEPLOYED_MAINNET_2026-07-08` (commit `74841caf`), **not
  `main`**, which has ABI drift.

### 4.3 The honest consequence

`identity_key` is per-contract, so **no unified cross-surface portfolio exists on-chain**. The "one
private account" view is a **client-side reconstruction from the viewing key**. This is stated in the
README. It is also the correct design — the alternative is a stable cross-surface pseudonym.

## 5. Markets — FPMM

**Mechanism:** constant-product AMM over binary UP/DOWN outcome tokens. Seeded ~$200/market; seeder
loss bounded by the seed. Math is u256 mul/div plus a ~20-line integer sqrt.

**Why not the alternatives:** CLOB is *legal* but economically dead (~$6–13 fees per fill at tens of
order messages per fill; ~22.7 s minimum requote; zero makers among ≤239 protocol users) — and Mysten
built the best on-chain CLOB in existence and **did not use it** for their own prediction market.
Parimutuel dilutes early bettors and hides your payout at bet time. LMSR needs exp/ln in Cairo for no
gain. House fixed-odds makes odds an admin constant, killing the RFP's aggregation thesis.

**What FPMM gives:** price locked at bet time · odds visibly move on every trade · **early exit** ·
works with **one** bettor.

**Per-bettor balances keyed by `ComputeAndInvoke`'s pool-derived `identity_key`** — no bearer coupon to
lose.

**Timeframes** (bounded by Pragma, not by the pool): **BTC/ETH/STRK · 1-hour flagship** · 1-day ·
1-month · 15-minute as an explicitly experimental tier with a void-and-refund rule. **Nothing shorter
— a 1-minute market is undecidable ~81–87% of the time.**

**Resolution:** snapshot `get_data_median` + `last_updated_timestamp` at deadline; require freshness
within ~120 s, else **void and refund**. `set_checkpoint` is verified permissionless, so we pin our own
settlement checkpoint.

**🚨 Pyth sunsets Starknet 26 Aug 2026 — five days before the deadline.** Chainlink is Sepolia-only.
Pragma is the only live oracle; its SummaryStats/TWAP contract is **not deployed**.

**The differentiator:** a 3-strike ladder is **one transaction, one fee**, and "claim all winnings" is
one transaction. Across ~1,248 `OpenNoteDeposited` events in protocol history, **nobody has ever
batch-settled.**

**A CLOB is named in the README as the design we rejected, with the measured numbers** — demonstrating
we read the protocol is exactly the 30% integration-depth signal.

## 6. Bridge — outbound only

`ValueRouter.BRIDGE_FORWARD` via CCTP v2. **Do not reinvent StarkWare's public Apache-2.0 reference**
at `starkware-libs/privacy-bridge`.

Marginal cost over the ValueRouter: **~90–115 Cairo lines** (+15–25 for variable `hook_data`).

**Freshness is genuinely solved on EVM:** Circle's Forwarding Service submits the destination mint and
pays gas from the minted USDC. A fresh address receives real USDC with **zero gas, zero actions, and
never signs anything** — verified 45/45 complete on live Starknet-origin burns.

**Solana is reachable** (270 all-time Starknet→Solana burns, 8 with the identical forwarding hook, all
complete, 9–16 s) **but a fresh Solana wallet has no token account and delivery reverts without one.**
StarkWare's contract hardcodes a zero-payload hook and **structurally cannot** request account
creation; ours can, via Circle's 65-byte extended hook (+~$0.185). **Settle with one ~$0.75 mainnet
probe before a single Solana word reaches the README or the video.**

**Destination UX (D25d):** default to a **fresh address**; allow pasting any address; **actively warn
when the pasted destination is the user's own connected wallet**, because that self-links and destroys
the privacy they just paid for.

**Never claim:** unlinkability · amount privacy · hidden deposits · timeout-and-reclaim (CCTP burns are
**irreversible**; a stuck crossing is resumable but never refundable) · "no history" for Solana (say
"no on-chain path back to the funding source").

## 7. App shell

- **Routes are modes.** Shield, unshield, send, swap and bridge share *pick asset → amount → review →
  confirm*: one component with a mode enum. Bridge is not a tab — it is what happens when the
  destination chain differs.
- **Build the amount input and asset selector first.** They are the spine; every later surface gets a
  familiar front door free.
- **One progress machine**, steps as data: `Built → Proved → Relaying → Settling → Spendable`. Handles
  **proof expiry** (450 blocks ≈ 13 min — detect and re-prove, never hang) and **pool paused/upgraded**
  (one global banner, one degraded mode). Row height is **constant**; any reflow reads as instability.
- **One transaction union → one renderer switch → one activity feed** across all six surfaces. Labelled
  as a client-side reconstruction.
- **Two components nobody else has:** the **disclosure panel** (what leaks · who can read it · **a way
  out**) and the **linkability meter** (the real crowd size, now).

## 9. Product experience

**No demo mode.** The app opens on a real account whose key is **published**, occupying the ordinary
account slot. Converting later is an ordinary account switch.

**First act:** one activity row is left undecrypted; pressing **Decrypt** runs real ECDH in the
visitor's browser against real ciphertext. Free, needs no identity, teaches the whole thesis — and it
is the only first act the bootstrap deadlock permits.

**Conversion triggers on intent only** — a primary CTA, `Receive`, or an invite link. Inline bordered
row, never a scrimmed modal; the composed form stays filled.

**Invite flow** — the fix for the app's most common hard error. On blur (before any proof is built) the
free `get_public_key` read fires; if zero, the form transforms: *"This address has no account on this
protocol… Send them an invite — we pay their registration."*

**Attached money is held as the sender's client-side intent, not relayer escrow** — every release from
one relayer identity would serialize globally on `INDEX_NOT_SEQUENTIAL`, and a row reading "from abu"
would be a provenance lie. When the recipient registers, **the sender's app opens the channel.**

**Backup:** generated Recovery Code + encrypted Recovery File, at conversion, gating registration.
Periodic verification on Signal's cadence.

**Four footguns answered honestly:** no rotation (offer a sweep to a new key, and state plainly that
the old key still reads everything ever sent there, including future notes) · ForeignKey collision ·
no watch-only (offer `Export activity` instead) · auditor escrow (rendered as **structure**, a calm
grey fee-row, never a warning — a warning implies a choice and there is none).

**A build-time lint fails on eight strings:** `end-to-end`, `E2EE`, `only you can`, `zero-knowledge`
(as a privacy claim), `watch-only`/`view-only`/`read-only`, `your address never appears`, `amounts are
private`, `unlinkable across surfaces`.

**No hardcoded numbers.** Fees come from `get_fee_amount()` at render (it is mutable — it was 4 STRK
earlier in history). Counts come from chain reads stamped with block height. **Durations do not render
until one real proof has been timed.**

## 10. Evidence and the gate

**Elimination gate** — miss one and the project is not scored: public repo + OSS licence · root
`strk20.json` · **≥3 verified SN_MAIN transactions that, since we deploy contracts, must run through
one of ours** · live public demo working **without login** · video ≤3 min · README.

### 10.1 Day-one probes — all four currently unproven

| Probe | Decides | Cost |
|---|---|---|
| Relayer end-to-end | Whether we may claim sender anonymity at all | ~150 LOC |
| `ComputeAndInvoke` round-trip (call twice from one wallet, once from another; first two `identity_key`s must match, third must differ) | Markets and launch both stake their privacy on it | ~1 day |
| Solana ATA probe | Whether Solana may appear in the README or video | **~$0.75** |
| **Time one real proof** | Whether a live video take is possible at all | free |

### 10.2 Week one

Deploy `MessageBook`, push **≥3 real mainnet transactions** through it. Chat is the only surface immune
to the coming default-deny screening flip (a zero-deposit invoke sets no screening subject), and its
zero-value invokes cannot revert on balances mid-demo.

**Mine-rule procedure:** keep `contracts: []` until transactions are banked, then add the router address
**in the same commit** as the transactions routed through it. The verifier passes a transaction matching
**any** declared contract, so listing two router versions is safe. `strk20.json` must use **flat bare-string
arrays**.

### 10.3 Login-free demo

| Surface | Cold visitor sees | Can do |
|---|---|---|
| Wallet | The persona's real shielded balance, decrypted live | Decrypt a row |
| Chat | A real decrypted conversation | **Send one message**, sponsored |
| Bridge | — | **Type an address, press send, watch real USDC land** |
| Markets / Launch / Swap | Live odds, curve, quote | Read |

3–5 personas pre-registered in week one; the published one is a **runtime config value**, so a drained
persona is a one-line redeploy. The persona's history renders from a **pinned block range**, so a rival
cannot write content into a screen a judge is reading.

### 10.4 Video

**A single crossing IS filmable live** — block time is 1.73 s, so one action is ~17 s of settling. A
full six-surface sequential run (~25–30 transactions) is not. Film one bridge crossing live; show the
rest as already-confirmed state. **Do not script until proof timing is measured.**

### 10.5 Standing risks

- **The pool is zero-delay upgradeable and pausable**, including during judging. Pin the class hash in
  the README, keep a lane that works while paused, **re-verify transaction links immediately before
  submission**.
- **The screening flip to default-deny** breaks every value-bearing helper. Chat is immune.
- Budget **~9.2–10.1 STRK median, ~14.3 p90** per pool transaction. Full six-surface demo ≈ 300–400
  STRK ≈ $8–11. **Money is not the constraint; time is.**
- Deposits are **mandatorily AML-screened**; a blocked address gets a silent revert that will look like
  our bug.

## 11. Claims that must never be made

Never: "fully anonymous" · "untraceable" · amount privacy for any open-note leg · that the deposit is
hidden · "end-to-end encrypted" · "watch-only" · that the latest code is fully audited (the audit is
scoped to commit `c5e2fb5`, May 2026) · that compliance is automatic · unlinkability for a bridge
crossing · timeout-and-reclaim.

Always disclose: the recipient of a private transfer sees the sender · anonymity sets are small and the
real number is shown on screen · the relayer sees network metadata · **the viewing private key is
escrowed on-chain to a StarkWare auditor, readable by anyone, with no rotation and no opt-out.**

The sponsor wrote the disclosure sentence for us (`MAINNET-DAY-0.md` line 108): *"Claim identity
privacy; never claim amount privacy for swaps."* Quoting them back is the cheapest defence available.
